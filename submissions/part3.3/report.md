## Current application

inspire runs on localhost using Vue, FastAPI, Python and SQLite. Home offers three independent activities: Emotion log, Guided breathing and Support chat. The user does not have to complete an emotion check-in before breathing or chatting. This remains a coursework skills prototype for fictional scenarios, not therapy, diagnosis or monitoring.

The emotion log combines personal color and explicit pleasantness × energy placement on one page, with optional notes and color meaning. Saved entries appear in calendar history and can be edited or deleted. Guided breathing uses a three-second countdown and six cycles of four seconds in and six seconds out. The application owns its clock, visual/audio cues, exits and session records; it does not ask the model to control the exercise.

Chat supports typing, dictation into an editable draft, and voice conversation with visible captions. The server-owned prompts support emotional exploration, relevant questions and practical answers when requested. Refusal and requests to stop take priority. Emergency remains an application-owned route throughout the experience, including request failures and overlays. Opening its U.S. resource panel does not contact anyone.

## Changes from the original plan

My [Part One plan](https://github.com/jclee2044/mental-health-app/blob/084981b0d18982257ee70371200c700fd6ba650c/report.md) started with a phone layout and a branding screen before the activity choices. I decided that a page containing only the app name and tagline did not add anything to the user experience, and wanted users to reach the activities directly. **TODO: reconcile this decision with the remaining 0.9-second skippable intro in `frontend/src/App.vue`; opening `#home` bypasses it, but the code has not completely removed it.** The Home page containing the three activities is still useful and remains.

I moved the pleasantness × energy graph into the first “How are you feeling today?” page rather than keeping a separate graph step. I also removed the separate feeling selection, so users no longer have to describe the same state through both a category and a graph. Personal color appears above the graph; notes and color meaning remain optional. I think this order makes more sense and reduces the number of steps. It follows D3's emphasis on minimizing emotional cost, although I have not measured an improvement in completion rates. The [assignment's findings](../../docs/assignment-description.md) support reducing demands; they do not establish a numerical relationship between this app's screen count and completion.

For the design, I added soft swirls and arcs that match the selected color theme. I wanted the shapes and transitions to communicate calm and smoothness, consistent with D6's low-stimulus presentation. Appearance now offers eight soft palettes, larger text and reduced motion. These are explicit user choices rather than automatic adaptation based on an inferred emotional state. A positive effect on emotion is my design intention, not an established outcome of this prototype.

Instead of sticking with a phone-only layout, I made the interface responsive to different screen sizes. I wanted to accommodate more ways of using the app and give users flexibility in how they interact with it. This expands the original layout without changing the three independent activity choices or requiring a particular device.

For guided breathing, I added tap-and-hold to encourage engagement and keep starting and stopping under the user's control. Releasing the circle ends the exercise, and the ending screen makes it clear that stopping is allowed (R3). Holding records a sustained input; it cannot establish that someone actually followed the breathing pattern. The tradeoff is that holding adds physical effort, so touch-device and accessibility usability still matter. Keyboard hold controls are also implemented.

I added human breathing sounds because I wanted users to feel less alone while following the pacing cue. I also added audio feedback for saving an emotion entry and completing or stopping breathing. I chose peaceful sounds, upward tones for a completed exercise and downward tones for an early ending to match my associations with completion and stopping. Emotion saves use a softened harp, completed breathing uses warm keys, and early endings use descending open tones. One global output-sound control lets the user turn playback off, while text and visual cues remain usable. The sounds are optional feedback rather than proof of participation or a therapeutic effect.

I chose not to implement eye tracking because establishing a meaningful baseline would add substantial complexity, and uncertain signals could lead to incorrect assumptions about the user's emotional state. I also wanted to avoid giving the model ambiguous signals that it might turn into unsupported interpretations. The app continues to use explicit self-report rather than passive emotion detection. These choices and the original evidence limits are documented in the [research notes](../../docs/research-notes.md).

## Saved history, personalization and model context

SQLite now stores emotion entries, breathing sessions, typed exchanges and accepted spoken text. Saved conversations can be reviewed and deleted, and separate model-generated titles make them easier to find. The application does not save audio recordings. Appearance and sound preferences are kept in browser local storage.

The original plan left historical context selection open. Personal memory now has three default-off permissions: recent emotion logs, saved conversation text and confirmed facts. With permission enabled, the server selects bounded context; this is broader than choosing an individual log for each reply. Saved-chat context uses a rolling seven-day window, preferring a valid cached summary and otherwise using a literal user excerpt. An opted-in saved chat can receive a separate cached model summary after it ends. These generated interpretations remain distinct from confirmed user facts. Voice receives one startup snapshot rather than continuous historical lookup. The [personal-memory contract](../../backend/app/features/personal_memory/CONTRACT.md) describes permission, selection and deletion boundaries.

I also implemented reviewed reframing references, extending the deferred retrieval proposal. The library has 19 active conversational cards covering fourteen core families plus supporting patterns. Typed matching uses embeddings and a separate SQLite vector index; voice can receive a compact startup catalogue. Personal history stays separate from this technique library. No separate vector-database server is required. The references are exploratory conversational material, not evidence that the NLP-style patterns are validated CBT or therapy. See the [library contract](../../backend/app/features/reframing/CONTRACT.md) and [content review](../../docs/reframing-content-review.md).

OpenAI processes the text or audio needed for provider-backed actions. Local SQLite storage does not mean all processing stays on the device. The model does not control Emergency, navigation, fixed breathing steps or saving. Only breathing has an implemented guided skill sequence; open-ended chat and optional reframing are not a completed guided one-minute reframe.

## Explanation of generated code

The AI-generated [`send()` function in `useChat.js`](../../frontend/src/features/chat/useChat.js) is directly relevant to that failure. It moves the submitted message into a bubble and clears the composer before awaiting the response, so the user can begin another draft. It captures a draft revision number. If the request fails, it marks that bubble as failed and restores the submitted text only if the draft has not changed. Otherwise, it leaves the newer draft alone and offers restoration of the failed message when the composer is empty.

The function queues a typed exchange for SQLite storage only after validating a successful reply. Generation and saving are separate operations, so retrying a failed save does not ask the model to answer again. An abort signal and active-state checks also prevent abandoned asynchronous work from being accepted after chat disposal. The [persistence contract](../../backend/app/features/voice/PERSISTENCE.md) documents the limits: pending saves stay in the loaded app and can be lost on reload or close.

### What I learned and what remains untested

A surprising live finding was that retrieval supplied `criteria` and `intention` cards for the listening-only prompt in all three runs, yet returned `no_match` for every explicit two-perspective request. The listener still respected “no advice.” The S04 replies therefore demonstrate general prompt/model behavior, not use of retrieved cards. My next decision is to review that query's relevance and the distinct-angle behavior before any separately authorized follow-up; I did not change the threshold or prompt during this run to improve the results.

Browser testing also found a gap that the earlier shared-state mocks missed: the emotion-deletion dialog put the sound control behind its backdrop, and clicking it closed the dialog without toggling sound. I moved sound access into the shared dialog component by default and added a regression test. Browser hit-testing, pointer/keyboard activation, nested Emergency and reload then passed. The [original failure and verified correction](../../docs/part33-browser-checks.md#s18-follow-up--fixed-and-verified) remain separately documented. This reinforced the need to test actual overlay interaction as well as shared state.

A specific untested limitation is real GPT-Live spoken delivery and interruption with the startup catalogue. Typed responses and mocked WebRTC lifecycle checks do not establish acoustic quality, reliable speech interruption or provider-side session closure. Broader safety/location cases, generated personal-memory accuracy, sustained conversations, touch/screen-reader usability and mocked peer observation also remain open. The fresh browser breathing-completion check remains tool-blocked; the earlier completion screenshot is not relabeled as a new run. Neither the recordings nor these checks establish clinical effectiveness.
